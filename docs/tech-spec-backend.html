Chat to paid order · Technical design · Backend and MCP · v2 · 27 Oct 2026

One Go service: the teammate's tools, the vendor's API, and the money path

A Go + Gin service on Railway with Postgres as the system of record and Redis for cache, locks, rate limits, idempotency and live events. It exposes an MCP endpoint the Chord teammate calls over Streamable HTTP, and a REST + SSE API the admin panel consumes. Payment truth comes from calling Paystack's verify endpoint, never from a webhook. This document is the contract: decisions and why, every endpoint with payloads, the schema, the transactions that move stock and money, what is cached and for how long, how it fails, what we promise, and how to run it at 2 am. Companion: tech-spec-web.html. Plan: plan.html.

System context

Three callers, one service, two backing stores, one external system. The Chord teammate is the only caller that can create an order. The admin panel reads, edits and listens. Paystack is only ever called by us; it never calls us. A customer's browser hits one page after paying.

01

Decision records

Each one is a choice that could have gone another way. The "revisit when" column is the trigger for reopening it, so nobody has to re-argue it until the trigger fires.

ADR-1 Postgres is the system of record; Redis is never the only copy of anything

Why: stock and money need row locks, unique constraints and a transaction that either moves a portion and marks an order paid or does neither. Redis holds derived or ephemeral state only: a cache that can be rebuilt, a lock that can expire, a counter that can reset, an event that can be missed and recovered by a refetch.

Consequence: Redis outage degrades latency and liveness of the board, never correctness. Revisit when: never for this product.

ADR-2 Redis is in from day one, with every use fail-open

Why: the vendor's board should feel live, a second replica should not double-serve a stale menu, login brute force should be rate limited across replicas, and admin writes should be safely retryable. Each is a Redis idiom. Putting it in now also exercises the deployment path under test conditions, which is the point of the exercise.

Consequence: an abstraction (cache.Store, locks.Locker, events.Bus) with a Redis implementation and an in-process fallback. Revisit when: a second replica is added (then the fallback must be disabled for locks).

ADR-3 Verify and confirm are separate tools; confirm re-verifies

Why: the conversation needs a "Paystack said yes" moment before stock moves, and reviewers should see two actions. A model may skip the first call, so the second never trusts it. Revisit when: telemetry shows the model skipping confirm_order after a successful verify more than 5% of the time; then fold them.

ADR-4 Stock is reserved at confirm, not at link creation

Why: a reservation at link time needs a release path for abandoned links and turns every "just checking the price" into a hold. A kitchen would rather sell the last portion twice and call one customer than hold it for a link that never pays. The paid_needs_attention state and the vendor's phone are the release path. Revisit when: needs-attention exceeds 2% of paid orders.

ADR-5 No Paystack webhook. Verify is the only source of payment truth; a reconciler polls for what the customer never reported

Why: the Paystack account is shared across several projects, so a webhook URL cannot be pointed at this service. That turns out to be the better design anyway: verify_payment and confirm_order each call GET /transaction/verify/:reference and read status, amount and currency from Paystack directly, so there is no signed-payload path to protect and no second source of truth. A customer who pays and closes WhatsApp without saying "paid" is caught by the reconciler, which re-verifies pending orders with a reference every 60 s and confirms the paid ones.

Consequence: confirmation lags a silent payment by up to ~3 minutes instead of being instant. No webhook_events table, no HMAC code, no inbound route from Paystack. Revisit when: this vendor gets a dedicated Paystack account; then a webhook can be added as an accelerator that calls the same ConfirmOrder.

ADR-6 Status columns are text + CHECK, not Postgres enums; ids are text slugs for menu, ULIDs for orders

Why: adding a status is a migration that edits a constraint, not an ALTER TYPE that cannot run in a transaction. Menu ids are human (jollof) because the model reads them. Order ids are ULIDs because they sort and are unguessable; order_no is the human handle.

ADR-7 Hand-written SQL, no ORM; goose for migrations, embedded

Why: under 30 queries, every one of which benefits from being readable in a review. Embedded migrations mean the binary is the deploy unit. Revisit when: query count passes ~80 or a second service shares the schema (then sqlc).

ADR-8 Stateless MCP transport, bearer auth, no OAuth

Why: Chord supports static bearer; OAuth needs dynamic client registration and an allowlisted redirect, which is a day on its own. Stateless means any replica answers any message. Revisit when: a second tenant needs its own credentials.

ADR-9 Separate deployables, same repo, no root build files

Why: the backend is Go and deploys to Railway from /backend; the frontend is Vite and deploys to Netlify from /frontend. Neither needs to know the other exists at build time. Root holds README.md, .gitignore and docs/ only. No Nx, no root package.json, no root Dockerfile.

04

Data model

Nine tables. Money is bigint kobo. Times are timestamptz. Status columns are text + CHECK (ADR-6). Postgres is the only place an order, a portion count or a confirmation exists.

DDL (the shape; 0001_schema.sql is the source of truth)

CREATE TABLE vendor_settings (
  id smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  vendor_name text NOT NULL, pickup_address text NOT NULL, rider_phone text NOT NULL DEFAULT '',
  order_prefix text NOT NULL DEFAULT 'TPK',
  prep_minutes int NOT NULL DEFAULT 40 CHECK (prep_minutes BETWEEN 5 AND 240),
  lunch_open time NOT NULL, lunch_close time NOT NULL, lunch_orders_close time NOT NULL,
  evening_open time NOT NULL, evening_close time NOT NULL, evening_orders_close time NOT NULL,
  pending_ttl_minutes int NOT NULL DEFAULT 30,
  low_stock_threshold int NOT NULL DEFAULT 3,
  version int NOT NULL DEFAULT 1,                      -- optimistic concurrency for PUT
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE menu_items (
  id text PRIMARY KEY CHECK (id ~ '^[a-z0-9-]{2,24}$'),
  name text NOT NULL, description text NOT NULL DEFAULT '',
  price_kobo bigint NOT NULL CHECK (price_kobo > 0),
  portions int NOT NULL CHECK (portions >= 0),
  available boolean NOT NULL DEFAULT true,
  window text NOT NULL CHECK (window IN ('lunch','evening','all')),
  sort int NOT NULL DEFAULT 100, photo_url text,
  version int NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE delivery_zones (
  id text PRIMARY KEY CHECK (id ~ '^[a-z0-9-]{2,24}$'), name text NOT NULL,
  fee_kobo bigint NOT NULL CHECK (fee_kobo >= 0), active boolean NOT NULL DEFAULT true, sort int NOT NULL DEFAULT 100
);

CREATE SEQUENCE order_no_seq START 231;

CREATE TABLE orders (
  id text PRIMARY KEY, order_no text NOT NULL UNIQUE,
  status text NOT NULL CHECK (status IN
    ('pending_payment','paid','paid_needs_attention','resolved','cancelled','expired')),
  customer_name text NOT NULL, phone text, note text,
  fulfilment text NOT NULL CHECK (fulfilment IN ('delivery','pickup')),
  zone_id text REFERENCES delivery_zones(id), address text,
  window text NOT NULL CHECK (window IN ('lunch','evening')),
  subtotal_kobo bigint NOT NULL, delivery_fee_kobo bigint NOT NULL, total_kobo bigint NOT NULL,
  reference text UNIQUE, authorization_url text, cart_hash text,
  source text NOT NULL DEFAULT 'mcp' CHECK (source IN ('mcp','admin')),
  paid_at timestamptz, ready_by timestamptz, confirmed_by text,   -- 'mcp' | 'reconciler'
  attention_reason text, resolved_at timestamptz, resolution_note text,
  expires_at timestamptz NOT NULL, reconciled_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX orders_open_cart ON orders (cart_hash) WHERE status = 'pending_payment';
CREATE INDEX orders_status_created ON orders (status, created_at DESC);
CREATE INDEX orders_pending_ref ON orders (created_at) WHERE status = 'pending_payment' AND reference IS NOT NULL;

CREATE TABLE order_lines (
  id bigserial PRIMARY KEY, order_id text NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  item_id text NOT NULL REFERENCES menu_items(id), name_snapshot text NOT NULL,
  unit_price_kobo bigint NOT NULL, qty int NOT NULL CHECK (qty > 0), line_kobo bigint NOT NULL
);

CREATE TABLE order_events (                                -- append-only audit trail per order
  id bigserial PRIMARY KEY, order_id text NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  type text NOT NULL,                                      -- created | link_issued | verified | confirmed | needs_attention | resolved | cancelled | expired
  actor text NOT NULL,                                     -- mcp | reconciler | admin:<id> | system
  data jsonb NOT NULL DEFAULT '{}', created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE payment_checks (
  id bigserial PRIMARY KEY, order_id text REFERENCES orders(id), reference text NOT NULL,
  source text NOT NULL, paystack_status text, amount_kobo bigint, currency text, gateway_response text,
  outcome text NOT NULL, latency_ms int, raw jsonb, checked_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE tool_calls (
  id bigserial PRIMARY KEY, tool text NOT NULL, args jsonb NOT NULL, result jsonb,
  ok boolean NOT NULL, error_code text, latency_ms int NOT NULL, order_no text, request_id text,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX tool_calls_created ON tool_calls (created_at DESC);

CREATE TABLE admins (
  id text PRIMARY KEY, email text NOT NULL UNIQUE, name text NOT NULL,
  password_hash text NOT NULL DEFAULT '', created_at timestamptz NOT NULL DEFAULT now()
);

Invariants the schema enforces

  • No negative stock: portions >= 0 is the last line of defence under the lock.
  • One Paystack reference, one order: reference UNIQUE.
  • One open order per identical cart: the partial unique index on cart_hash survives a race the Redis lock might miss.
  • Optimistic concurrency on vendor-edited rows: version on settings and items; a stale PUT/PATCH gets 409.

Retention

tool_calls and payment_checks are pruned to 90 days by the reconciler's nightly pass. Orders and order_events are kept. Customer phone and address are masked in tool_calls.args at write time.

05

Migrations and the seed

Boot sequence

  1. config.Load() fails fast on any missing variable and refuses PAYSTACK_FAKE=1 alongside a live-looking key in release mode.
  2. pgxpool.New, ping 5 s. redis.NewClient, ping 2 s; on failure log WARN and start in degraded mode (§07), do not exit.
  3. Take the Redis lock migrate:lock (PX 120000) so two replicas booting together do not race goose; fall through if Redis is down (goose uses its own table lock anyway).
  4. goose.Up over embedded migrations/.
  5. Admin password bootstrap (once). Warm the menu cache. Start the reconciler. Mount routes. Listen.
  6. /healthz reports ready:false until step 5 completes, so Railway does not route traffic to a half-migrated instance.

The two transactions that matter

CreateOrder (sequence)

 1. settings, menu ← cache.Get("menu:v1")  (Redis → memory → DB, §07)
 2. window check                        → window_closed
 3. each line: offered? qty ≤ portions? → item_unknown | item_unavailable{max_qty}
 4. zone/address rules                  → zone_required | address_required
 5. totals in kobo
 6. cart_hash
 7. lock ← locks.Acquire("cart:"+hash, 10 s)   advisory; skip if Redis down
 8. BEGIN
      SELECT … WHERE cart_hash=$1 AND status='pending_payment'
        hit, not expired → COMMIT, release, return reused=true
      order_no ← nextval; INSERT orders(status='pending_payment', expires_at=now+TTL)
      INSERT order_lines; INSERT order_events(created)
    COMMIT
 9. Paystack initialize (8 s)
      ErrUnavailable / Rejected → UPDATE status='cancelled', order_events(init_failed); return error
      ok → UPDATE reference, authorization_url; order_events(link_issued)
10. release lock; events.Publish(order.created); return

Step 3 is a soft check against the cache. Stock is reserved only at confirm (ADR-4). Between 8 and 9 there is an order with no reference for up to 8 s; the reconciler cancels any such order older than 2 minutes (a crash between the two steps).

ConfirmOrder(ref, actor) (sequence)

 1. order ← by reference                → unknown_reference
 2. terminal already? return it, already_confirmed=true
 3. lock ← locks.Acquire("confirm:"+ref, 20 s)
      held by another caller → wait up to 3 s then re-read step 2
 4. verify ← Paystack verify (8 s)      outside any tx
    INSERT payment_checks(source=actor)  always
    outcome ≠ success → release; return outcome
 5. BEGIN
      SELECT * FROM orders WHERE id=$1 FOR UPDATE
      terminal now? COMMIT; return already_confirmed
      SELECT id, portions FROM menu_items WHERE id = ANY($ids) ORDER BY id FOR UPDATE
      short := lines where portions < qty
      none short:
        UPDATE menu_items SET portions = portions - qty, version = version + 1 …
        UPDATE orders SET status='paid', paid_at, ready_by, confirmed_by=actor
        INSERT order_events(confirmed)
      else:
        UPDATE orders SET status='paid_needs_attention', paid_at, attention_reason, confirmed_by
        INSERT order_events(needs_attention)
    COMMIT
 6. cache.Del("menu:v1"); events.Publish(order.updated, menu.updated)
 7. release lock; return

The Redis lock shortens contention; the FOR UPDATE is the guarantee. Two actors can call this (model, reconciler) and exactly one decrement happens.

07

Redis: what it holds, and what happens without it

Six uses, each behind a small interface with a Redis implementation and an in-process fallback. Every use fails open: when Redis is unreachable the service keeps serving with weaker guarantees and logs it, because the strong guarantees live in Postgres (ADR-1).

UseKeys and commandsWhy RedisWithout Redis
Menu cachemenu:v1 → JSON {settings, items, zones}. GET / SET EX 5 / DEL on every write and confirm.Shared across replicas; one invalidation reaches all.In-process cache with the same TTL. Two replicas could serve 5 s-stale counts; soft check only.
Lockslock:confirm:{ref}, lock:cart:{hash}, migrate:lock. SET NX PX, release via compare-and-delete Lua.Serialises confirm across replicas and actors before the DB lock, so the second caller waits instead of blocking a connection.Process-local mutex map. Correctness still from FOR UPDATE and unique indexes.
Rate limitsrl:login:{ip}, rl:paid:{ip}, rl:mcp. INCR + EXPIRE fixed window; Lua for atomicity.Brute-force protection must count across replicas.In-process limiter per replica (N× looser). Logged WARN.
Idempotencyidem:{admin_id}:{Idempotency-Key} → {status, body hash, body}. SET NX EX 86400.Admin POST/PUT/PATCH replay the stored response on retry; a different body with the same key is 422.Header ignored; writes are still safe because they are version-checked (409 on stale) and the reset is idempotent by construction.
Event busChannel events; messages {type, order_no?, at}. PUBLISH / SUBSCRIBE.Any replica's write reaches every replica's SSE clients.In-process bus; only same-replica clients hear it. SSE still sends a 15 s heartbeat and the client's 30 s safety refetch covers the gap.
JWT revocationjwt:revoked:{jti} SET EX (remaining lifetime). Checked on every admin request.Logout and "change password" invalidate live tokens.Tokens valid until expiry (24 h). Documented.

What is deliberately not in Redis

  • Paystack verify results. Never cached. Every verify_payment and every confirm asks Paystack.
  • Stock counts as the source of truth. Redis holds a 5 s copy for display and soft checks only.
  • Sessions. The JWT is the session.
  • Queues. The reconciler is a ticker over Postgres; a job queue would be a fourth system for one job.

Client settings

redis.Options{ Addr: cfg.RedisURL, DialTimeout: 2s, ReadTimeout: 300ms, WriteTimeout: 300ms,
               PoolSize: 10, MinIdleConns: 2, MaxRetries: 1 }
// every call: ctx with 300 ms deadline; on error → fallback path + metric redis_fallback_total{use}
Degraded mode is a first-class state. /healthz reports "redis":"degraded" and stays ok:true. The board shows a quiet "live updates paused" chip. Nothing in the money path depends on Redis.
08

The MCP endpoint

Chord is the MCP client. JSON-RPC 2.0 over Streamable HTTP: one POST /mcp per message, JSON or SSE back. Stateless (ADR-8), so Chord needs no session id and any replica answers.

Wiring

srv := mcp.NewServer(&mcp.Implementation{Name: "iya-bisi-ordering", Version: build.Version}, nil)
mcp.AddTool(srv, &mcp.Tool{Name:"get_menu",       Description: d.GetMenu},       activity.Wrap("get_menu",       tools.GetMenu))
mcp.AddTool(srv, &mcp.Tool{Name:"create_order",   Description: d.CreateOrder},   activity.Wrap("create_order",   tools.CreateOrder))
mcp.AddTool(srv, &mcp.Tool{Name:"verify_payment", Description: d.VerifyPayment}, activity.Wrap("verify_payment", tools.VerifyPayment))
mcp.AddTool(srv, &mcp.Tool{Name:"confirm_order",  Description: d.ConfirmOrder},  activity.Wrap("confirm_order",  tools.ConfirmOrder))

h := mcp.NewStreamableHTTPHandler(func(*http.Request) *mcp.Server { return srv },
       &mcp.StreamableHTTPOptions{Stateless: true})

r.POST("/mcp", requestID(), mcpBearer(cfg.MCPToken), ratelimit.MCP(), bodyLimit(64<<10), timeout(20*time.Second), gin.WrapH(h))
r.GET("/mcp",    methodNotAllowed)
r.DELETE("/mcp", methodNotAllowed)
  • Input structs carry json and jsonschema tags; the SDK generates inputSchema, which is what Chord's tools probe shows.
  • Tool descriptions live in mcpserver/descriptions.go and say when to call the tool and what to do with the result; they are part of the prompt the model sees.
  • Chord's request id, if any, is propagated as request_id into tool_calls and logs.

Timeouts 8 s. One retry on a network error for verify (idempotent); none for initialize (may have created the transaction). Fake client (PAYSTACK_FAKE=1): initialize links to our own /paid?ref=…&fake=1; verify is success once that page was visited, abandoned before, failed for totals ending in 99.

Why there is no webhook

The Paystack account behind sk_test_… is shared by several projects, so its single webhook URL cannot point here. The design does not need it: every decision about money is made by calling GET /transaction/verify/:reference at the moment of the decision. The model's "paid" triggers a verify; confirm_order verifies again inside its own call; the reconciler verifies on a timer. Three readers, one source of truth, no inbound surface from Paystack to secure.

If a dedicated account appears later: add POST /webhooks/paystack with HMAC-SHA512 over the raw body, dedupe on Paystack's event id, and call the same ConfirmOrder(ref, actor=webhook), which re-verifies anyway. It becomes an accelerator; nothing else changes.

Reconciler (ADR-5)

every 60 s, under lock "reconcile:tick" (PX 55000):
  1. pending orders with reference, created > 2 min ago, reconciled_at null or > 5 min ago, limit 20:
       verify; success → ConfirmOrder(actor=reconciler); else set reconciled_at
  2. pending orders with NO reference, created > 2 min ago → cancelled, order_events(init_lost)
  3. pending orders past expires_at whose last check ≠ success → expired
  4. once a day at 03:00 WAT: prune tool_calls / payment_checks older than 90 days

Verify calls per minute ≤ 20, so the reconciler can never exhaust Paystack's rate limit. Every pass emits reconcile_orders_total{result}.

What this buys: a customer who pays and never types "paid" shows up on the board within about 3 minutes, with no webhook involved.

  • Postgres pool 8; each confirm holds a connection ≤ 50 ms inside the tx (verify happens outside).

Mechanics

  • JWT: HS256, JWT_SECRET 48 bytes; claims sub, email, jti, tv (token_version), iat, exp 24 h. Sent as Authorization: Bearer; stored by the frontend in memory + localStorage (web spec §06). No cookies, so Netlify ↔ Railway needs no SameSite work.
  • CORS on /api/* only: exact-match CORS_ORIGINS (Netlify prod URL, *.netlify.app deploy previews matched by suffix, http://localhost:5173). Methods GET POST PUT PATCH OPTIONS; headers Authorization, Content-Type, Idempotency-Key, If-Match, Last-Event-ID; Vary: Origin; max-age 600. /mcp gets no CORS headers.
  • Headers: X-Request-ID accepted or generated and echoed; Cache-Control: no-store on all API responses; X-Content-Type-Options: nosniff.
  • Gin release mode; TrustedProxies = Railway's; ClientIP() feeds rate limits.
  • /metrics behind METRICS_TOKEN so it is not a public enumeration of our internals.

Rollout and rollback

  • Deploy = push to main (Railway GitHub integration, watch path backend/**) or railway up from backend/.
  • Migrations are forward-only and additive; a rollback is redeploying the previous image, which still runs against the newer schema. A destructive migration ships in two releases (add → migrate data → drop later).
  • Health check gates traffic; a failed migration fails the deploy and the previous instance keeps serving.
