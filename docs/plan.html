01

The vendor and the one job

A home kitchen in Surulere that cooks for offices and homes nearby. Lunch 11:00 to 15:00, evening 17:00 to 20:30. The vendor answers "what's on the menu", "is jollof still available" and "how much with delivery" all day, takes orders by hand, then chases transfers and matches them to names. Orders get lost between "I want" and "I've paid", items get oversold, and she cannot cook while typing.

The seed is a CSV per tab in sheet-template/ plus a cmd/seedsheet command that writes it into your Sheet, so a bad test run never costs us the demo state.

The one job, start to finish

  1. Menu. Customer asks what's available. Agent reads the sheet: items in the current window with portions left, prices, delivery fees.
  2. Order. Items, quantities, delivery or pickup, address, name. Agent validates against stock and the cut-off, computes the total with delivery, writes a pending order, creates the Paystack transaction, returns the link.
  3. Pay. Customer pays on Paystack's test checkout.
  4. Verify, then confirm. On "paid", the server asks Paystack. Only a verified success leads to confirm_order, which re-checks stock, decrements it, and marks the order paid with an order number. Once per reference.
  5. Confirm to the customer. Order number, what's in it, where it's going, ready-by time.

Deliberately left out (said in the problem statement)

  • Delivery dispatch and rider tracking
  • Refunds (a paid order whose item sold out is flagged to the vendor, not refunded by the agent)
  • Multiple vendors; menu creation from photos (the next step, in the go-live note)
  • Customer accounts and order history
  • Pidgin or Yoruba beyond a light touch; gadget-specific needs (serials, warranties, pay on delivery)

Why this scores

Integration 25%

Two real systems: Paystack (initialize, verify) and a Google Sheet the tools read and write. Stock goes down only when payment is verified. Pending, abandoned, failed, amount-mismatch, sold-out-after-payment, Sheet errors and Paystack-down are all handled, not ignored.

Field notes 25%

Our own MCP server on Railway, plus the Sheets API with a service account. Both will produce real problems. We log them as they happen.

Problem choice 20%

Every Nigerian city has these vendors. Measurable: orders taken without the vendor typing, chat-to-paid conversion, oversold items. It sits next to Paystack Index (agents buying from merchants), which shows we read where TSG is going.

The paths that are not happy

"paid" before paying

Paystack says abandoned or pending → not_confirmed. Agent: "I can't see it yet. The link is still open; finish the payment and tell me again. If you paid by transfer, give it a minute." Never "failed".

Card declined

failed with a gateway reason. Agent repeats it in plain words and offers a fresh link for the same order. Nothing is confirmed, stock untouched.

Sold out between menu and order

create_order returns item_unavailable with max_qty. Agent: "Ofada just ran out (only 1 left). Want 1, or swap for jollof?"

Sold out after payment

confirm_order re-checks stock. If gone, the order is marked paid_needs_attention, nothing is decremented, and the agent says Iya Bisi will contact them to swap or sort it out. Refund is out of scope and the agent says so. The board shows it in red.

After the cut-off

window_closed with next_window. "Lunch orders closed at 14:30. Evening menu opens 17:00, shall I take it for then?"

Quantity above stock

Offer the maximum available, never silently reduce.

"paid" twice

Same reference, same order, same reply. No second order, no second decrement.

Paystack or the Sheet is down

paystack_unavailable / store_unavailable. "Our ordering system isn't responding right now, nothing has been charged. Try again in a few minutes or message Iya Bisi directly on this number."

The four tools

Money is returned twice: kobo integers for correctness, formatted naira strings for the model to repeat. The model never adds up a cart. The server never trusts the model about money or stock.

confirm_order {reference} {order_no, status paid | paid_needs_attention | already_confirmed, lines, total_display, fulfilment, address, ready_by, attention_reason?}. Server re-verifies with Paystack before writing, re-checks stock, decrements, writes status and paid_at. Idempotent on reference. Paystack verify (again) · Sheet: update order row, update menu portions

Why verify and confirm stay separate, and why confirm re-verifies

The handoff keeps them separate so the conversation has a clear "Paystack said yes" moment before stock moves, and so a reviewer can see two distinct actions in the activity log. The cost is a model that might forget the second call. So verify_payment tells it what to do next, the skill says it twice, and confirm_order does its own Paystack check, so calling it without verify is safe and calling verify without confirm leaves a visibly unconfirmed paid order on the board for the vendor.

Rules the code enforces, independent of the skill

  • Kobo integers. The sheet holds naira for the vendor's sake; the server parses to int64 kobo on read and refuses non-integer naira with a clear store_invalid_price error that names the row.
  • Stock moves only in confirm_order, under a process-wide mutex around the read-modify-write, because Sheets has no transactions. Single instance on Railway; the go-live note says a database replaces this before real use.
  • Verify checks amount and currency, not just status. Mismatch is flagged for the vendor, not confirmed.
  • Idempotency. confirm_order on an already-paid reference returns the stored order. create_order with the same cart_key and an open pending order under 30 minutes old returns it with reused: true, so "send the link again" does not make a second Paystack transaction.
  • Pending is not failed. Paystack abandoned, pending, ongoing, processing, queued → not_confirmed. Only failed, reversed → failed.
  • Cut-off is server time in WAT, from the settings tab. The skill never decides whether the kitchen is open.
  • Every call is logged (args, result, error code, latency) to the activity log, in SQLite even when the store is Sheets, so the board and the field notes have it.

SKILL.md outline (under 1,500 words)

  1. Who you are: the ordering assistant for Iya Bisi's Kitchen. Warm, brief, Nigerian English, one question at a time, no emojis beyond one per message.
  2. Menu comes from get_menu, always fresh. Call it at the start of every order and again if more than a few minutes passed. Show items with price_display and portions left. Never list an item the tool did not return.
  3. Collect before ordering: items and quantities, delivery or pickup, zone and address if delivery, a name. Ask for what's missing, one thing at a time.
  4. Then create_order. Repeat its lines and total_display exactly, then the link and reference. Say "tell me paid when done".
  5. On "paid": verify_payment, then if success, confirm_order. Only after confirm returns paid say the order is confirmed, with order_no and ready_by.
  6. not_confirmed is "not yet", never failed. failed: say the gateway reason plainly, offer a new link.
  7. paid_needs_attention: apologise, say Iya Bisi will contact them to swap or sort it out, do not promise a refund.
  8. Errors: say the tool's message. Do not guess a cause. If the system is down, give the vendor as the fallback.
  9. Out of scope: rider tracking, refunds, complaints about a delivered order → "please message Iya Bisi directly".

What the model must never do

  • Quote a price, a total or a portion count from memory.
  • Say "confirmed" before confirm_order returns paid.
  • Say "failed" for a pending or abandoned payment.
  • Decide the kitchen is open or closed; the tools do.
  • Call create_order twice for the same cart; ask for the link again via the same call with the same cart_key.
  • Invent items, delivery times, rider details or refunds.
  • Use em dashes or "it's not X, it's Y".
Test the skill in the in-app chat first, not the simulator. Each turn costs credits; the in-app run is the one place we can afford a second try.

The identity question

The simulator does not give the agent a phone number. The agent asks for a name, and a phone only for delivery. No accounts, no lookup. That is in the go-live note as "customers are whoever they say they are; the order number is the identity".

Your part: Google Sheet and service account

About 20 minutes of clicking. Hard budget 30. Needed before stage 3 (deploy). If anything here fights you, say so and we ship on SQLite; the attempt itself is a field note.

A · the service account (Google Cloud)

  1. Open console.cloud.google.com with the Google account you want to own this. Top bar → project picker → New project → name chat-to-order → Create, then select it.
  2. Enable the API: left menu → APIs & Services → Library → search "Google Sheets API" → Enable. (Drive API is not needed; we never create files, only read and write one you share.)
  3. Create the service account: IAM & Admin → Service Accounts → Create service account → name vendor-sheet-bot → Create and continue → skip roles (none needed) → Done.
  4. Make a key: click the account → Keys tab → Add key → Create new key → JSON → Create. A .json file downloads. Treat it like a password.
  5. Copy its email: on the same page, the address looks like vendor-sheet-bot@chat-to-order.iam.gserviceaccount.com. You need it in step B3.
  6. Encode the key for env: in a terminal, base64 -i ~/Downloads/chat-to-order-xxxx.json | tr -d '\n' | pbcopy. Paste into backend/.env as GOOGLE_SERVICE_ACCOUNT_JSON_B64=… and later into Railway. Then delete the downloaded file or move it out of any repo folder.

B · the Sheet

  1. Go to sheets.new. Name it Iya Bisi's Kitchen (demo).
  2. Rename the first tab to menu. Add two more tabs named exactly orders and settings. Leave them empty; seedsheet fills them.
  3. Share (top right) → paste the service account email from A5 → role Editor → untick "Notify people" → Share.
  4. Copy the sheet ID from the URL: the long string between /d/ and /edit. Put it in backend/.env as GOOGLE_SHEET_ID=…. The ID is not a secret.
  5. Tell me "sheet ready". I run go run ./cmd/seedsheet, which writes the three tabs from sheet-template/. Open the sheet and confirm the 8 menu rows are there. That is also the first Sheets API call, so any auth problem shows up here, on my machine, before Railway.
  6. Keep the sheet open in a tab for the recording; the orders row appearing in the vendor's own sheet is the integration proof.
Common failures and what they mean: 403 The caller does not have permission → the sheet is not shared with the service account email, or shared as Viewer. 404 Requested entity was not found → wrong sheet ID. 403 Google Sheets API has not been used in project → step A2 skipped. Each of these is a one-line fix and a field note if it happened.

Role: Forward-deployed Engineering (second choice: Technical Product Management).

Iya Bisi runs a home kitchen in Surulere and sells lunch and dinner to offices and homes nearby over WhatsApp. She answers the same questions all day, takes orders by hand, matches bank transfers to names from screenshots, and oversells dishes because the count lives in her head. Go-live note for Iya Bisi (half a page)

  • What it does: shows your menu from your sheet, takes orders, sends a Paystack link, confirms only paid orders, lowers your portion counts, and shows you a board of today's orders.
  • What it does not do: send riders, give refunds, handle complaints, or add dishes by itself. You update the sheet each morning.
  • Before real customers: live Paystack keys and your settlement account; your WhatsApp Business number connected to Chord; real prices and portions in the sheet; a one-week trial with regulars you trust; a Chord credit top-up and someone watching it.
  • When a payment fails: the customer sees the bank's reason and gets a new link. Nothing is recorded. You see it on the board.
  • When a dish runs out after someone paid: the order shows in red as "needs you". You call them to swap or refund by transfer yourself.
  • When something breaks: the agent tells customers to message you directly and nothing is charged. The board's Activity page shows the error. Who gets alerted: you, by WhatsApp (to be set up); Feranmi for the service.
  • Honest risks: the sheet is a spreadsheet, so two orders at the exact same second could over-count once (a database fixes this); the assistant can misread a message; customers are whoever they say they are, the order number is the identity.
  • Next: menu from photos you snap; gadget vendors need stock counts, warranties and pay-on-delivery, not built.

Risks and fallbacks

Sheets access fights us

Service account permissions, API not enabled, quota, or slow writes.

Plan: 30 minutes, then STORE=sqlite. Same tools, same conversation, same board; only the vendor's editing surface changes. Field note explains it; go-live note says "move to a sheet or a database the vendor can see".

Chord cannot use our MCP server

Transport, auth, outbound policy, timeouts.

Plan: 45 minutes of real debugging with the health probe and server logs. Past H+5:00, switch the teammate to Chord's built-in Paystack connector (TSG confirmed it qualifies) and write up exactly what failed and what Chord should change.

Credits run out

Tool-using turns cost more; a menu listing is a long reply.

Plan: everything tested locally with the fake first; in-app before simulator; measure after the first run; hard stop at 35. At 40, email Emmanuel at once.

The model misbehaves with money or stock

Says confirmed early, invents a price, double-orders.

Plan: the server never trusts it: confirm re-verifies, stock moves once per reference, create reuses by cart_key. Worst case is a wrong sentence, never a wrong sheet. Tighten the skill, republish.

Sold-out race

Two customers pay for the last portion at the same time.

Plan: single instance plus a mutex handles the demo. The second confirm gets paid_needs_attention, which is the honest answer. Documented as a go-live risk.

Running out of day

Everything takes longer than written.

Plan: the cut lines in §13. The minimum is stage 4 plus the written pieces. A board-less submission with honest notes scores; a half-built board with no field notes does not.
