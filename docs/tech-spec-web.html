The vendor's panel: a board the vendor watches and a few things they edit

React 19 + TypeScript on Vite, TanStack Router for routes, TanStack Query for data, Tailwind v4 for styling, deployed to Netlify from /frontend. It talks only to the backend's REST + SSE API (tech-spec-backend.html §11). This document is the contract for the app: decisions, folder structure, routing, the data layer and how it stays live, auth, the design system adapted from Ohlify's contracts with this product's skin, every screen with every state, the error contract, build, deploy and tests. 00

Context

One user (the vendor, or Feranmi during the demo). One device class that matters (a phone propped in a kitchen) and one that matters for the recording (a laptop). The panel is read-mostly: it watches orders arrive and lets the vendor fix stock, settings and the rare order that needs her.

01

Decisions

ADR-W1 Separate deployable in /frontend, Netlify, no root build files

Why: static hosting with deploy previews for free, zero coupling to the Go build, and a CDN edge for the kitchen's phone. Everything the app needs (package.json, netlify.toml, vite.config.ts, lockfile) lives inside frontend/. The repo root stays README.md, .gitignore, docs/.

ADR-W2 TanStack Query owns every byte of server state; React state owns only UI state

Why: no Redux, no Zustand, no duplicated caches. A screen is a composition of query hooks plus local useState for things like "which row is expanded". Mutations invalidate by key; SSE invalidates by key; the two never fight because invalidation is idempotent.

ADR-W3 SSE carries ids, not payloads; every event is a refetch

Why: a missed or reordered event can never show a wrong number, only a late one. The cost is one small GET per event, which at ≤ 60 orders a day is nothing. When SSE is down the same keys poll every 30 s.

ADR-W4 Bearer JWT in memory, mirrored to localStorage; no cookies

Why: Netlify and Railway are different origins; a cookie would need SameSite=None and a CSRF story. A bearer header is simpler, the backend revokes on logout, and the panel holds no customer PII beyond what the order rows show. localStorage access is wrapped in try/catch and the app works without it (login per tab).

ADR-W5 Ohlify's contracts, this product's skin

Why: the PASS/BOARD law, the semantic quartet, the disabled/readOnly/error triad and the overlay contract are the parts of Ohlify that stop a team improvising. The violet, Mona Sans and hairline-first elevation are Ohlify's identity, not ours. We keep the laws, swap the tokens, and add one rule: PASS blocks get the 2 px ink border and offset shadow; BOARD blocks get hairlines.

ADR-W6 Feature-sliced folders, file-based routes, no barrels in features

Why: a feature is deletable with one rm -rf. Routes are thin files that import a screen. Shared code is promoted only when a second feature needs it.

ADR-W7 Money and time are formatted by the backend; the UI renders strings

Why: one formatter, one timezone, no Intl drift between the WhatsApp reply and the board. The UI uses *_display and *_wat fields and never divides by 100.

Data layer

Client

// shared/api/client.ts
export async function api<T>(path: string, init: ApiInit = {}): Promise<T> {
  const ctrl = new AbortController(); const t = setTimeout(() => ctrl.abort(), init.timeoutMs ?? 10_000);
  const res = await fetch(`${BASE}${path}`, {
    ...init, signal: ctrl.signal,
    headers: { 'Content-Type': 'application/json', Accept: 'application/json',
      ...(auth.token ? { Authorization: `Bearer ${auth.token}` } : {}),
      ...(init.idempotencyKey ? { 'Idempotency-Key': init.idempotencyKey } : {}),
      ...(init.ifMatch !== undefined ? { 'If-Match': `"${init.ifMatch}"` } : {}),
      ...init.headers },
  }).finally(() => clearTimeout(t));
  if (res.status === 204) return undefined as T;
  const body: unknown = await res.json().catch(() => null);
  if (!res.ok) throw ApiError.from(res, body);        // §10
  return init.schema ? init.schema.parse(body) : (body as T);
}
  • BASE = import.meta.env.VITE_API_BASE_URL, validated at boot by zod (must be https in production).
  • Every hook passes a zod schema; a parse failure is an ApiError with identity contract_drift and is reported, not swallowed.
  • 401 anywhere → auth.clear() and redirect to /login?next=, except on /auth/login itself.
  • Mutations send a fresh crypto.randomUUID() as Idempotency-Key per user action, reused across retries of that action.

Optimistic updates: two, deliberately

useUpdateItem for available toggles and portions edits applies optimistically with If-Match; on 409 it rolls back and shows "Changed elsewhere, reloaded" with the server's current value. Nothing else is optimistic: resolving or cancelling an order waits for the server, because the board is the vendor's record.

Live updates

The stream

// features/live/utils/use-event-stream.ts
// fetch + ReadableStream reader, because EventSource cannot send Authorization.
state: 'connecting' | 'live' | 'degraded' | 'offline'
connect():
  GET /api/v1/events  (Authorization, Last-Event-ID if we have one)
  parse "event:" / "data:" / "id:" frames; comment lines are heartbeats
on open:  state=live; queryClient.invalidateQueries()      // full refetch on every (re)connect
on event:
  order.created | order.updated → invalidate ordersAll, stats, order(order_no)
  menu.updated                  → invalidate menu, stats
  settings.updated              → invalidate vendor, menu, stats
  reset                         → invalidate everything
  degraded {on:true}            → state=degraded (polling kicks in); {on:false} → live
on error/close: backoff 1s → 2s → 4s → … 30s, jittered; state=connecting; after 3 failures state=offline
heartbeat watchdog: no bytes for 45 s → close and reconnect
  • One stream per tab, owned by LiveProvider under the authed layout; torn down on logout.
  • Pauses when document.hidden for > 60 s and reconnects on visibility, which is also a full refetch.

Polling as the fallback, not the default

const live = useLive();                       // from LiveProvider
useQuery({ ...statsQuery, refetchInterval: live.state === 'live' ? false : 30_000 });

Board, orders list and activity use this pattern. Detail, menu and settings do not poll; they refetch on focus and on events.

06

Auth

Flow

  1. Boot: read auth.token from storage.get('ctpo.token') (try/catch). If present, GET /auth/me; 200 → authed, 401 → clear.
  2. /login: email + password form (zod), POST /auth/login. On success store {token, expires_at, admin} in the provider and mirror the token to storage. Navigate to next or /.
  3. Every request adds the bearer. Any 401 clears and redirects with next.
  4. Logout: POST /auth/logout (revokes jti), then clear, then close the SSE stream, then navigate to /login.
  5. A timer at expires_at − 5 min shows a quiet "session ends soon, sign in again" banner. No silent refresh (there is no refresh token).
// features/auth/providers/auth-provider.tsx
interface AuthValue { status: 'loading'|'anon'|'authed'; admin: Admin|null; token: string|null;
                      login(email, password): Promise<void>; logout(): Promise<void> }

Rules

  • The token is never put in a URL, a log, or a query key.
  • storage.ts wraps localStorage; every call is try/catch and returns null on failure. Private mode works, with login per tab.
  • Rate-limit 429 on login shows the real Retry-After seconds and disables the button for that long.
  • The login screen is the only route outside the authed layout. There is no sign-up, no forgot-password (one admin, set by env; documented in the go-live note).
Deploy previews on Netlify get their own origin. The backend's CORS allowlist matches *.netlify.app by suffix for previews, so a preview can log in against the Railway backend with the same admin.
07

Design system: Ohlify's laws, this product's skin

From Ohlify we take the contracts. From the plan we take the look: leaf green, Nunito, Baloo 2, JetBrains Mono, warm paper, 2 px ink borders, offset shadows, light only.

The laws we keep

LawMeaning here
Two zones: PASS and BOARDA PASS is what one person holds: a stat tile, an order's total, the login card, a settings form. Fierce hierarchy, one big figure, 2 px ink border, offset shadow, radius 12/8. A BOARD is what an operator scans: the orders list, the menu table, the activity log. Columnar, hairline-ruled, tabular numerals, radius 8/4, many rows at one weight. A screen may hold both; a single block belongs to exactly one. A board row never gets a display-size figure; a stub never appears in a table cell.
A live figure flips, never tweensStock counts, totals, order counts update digit-in-place. No count-up, no number tween.
The semantic enum, five values, each a quartetneutral · info · success · caution · critical, each with base / soft / onSoft / border. Used verbatim by chip, badge, callout, toast, banner, form validation. No component mixes its own tint.
Hazard is never a button"Needs attention" is a state the system reports in critical red. The only red button is a destructive confirm (Cancel order, Reset demo), which needs a typed word.
disabled / readOnly / error are independentEvery input takes all three. A readOnly field keeps full ink contrast (the order number, the Paystack reference). readOnly + error is allowed.
Variant × modifier, never a flat cross-productButton: variant: solid | outline | plain | ghost, destructive: boolean, size: sm | md | lg. No textStyle or radius escape hatches.
One overlay contractModal, drawer, popover, menu: open / onOpenChange / Trigger / Portal / Content. Scrim 0→.5 in 200 ms; content scale .96→1 + fade in 280 ms ease-out, trailing the scrim by 40 ms.
Typed confirm for the irreversibleCancel order: type CANCEL. Reset demo: type RESET. Button disabled until exact match.
Every data component ships its own skeletonNot one shimmer box. StatTile.Skeleton, OrderRow.Skeleton, ToolCallRow.Skeleton match the real layout.
The one reconciliation. Ohlify is hairline-first and reserves shadow for overlays. This product wants 2 px ink borders and offset shadows. Resolution: PASS blocks carry the ink border and the offset shadow (they are card stock); BOARD blocks carry hairlines only (they are instruments). Overlays get the ink border and a larger offset. Nothing else gets a shadow.

  • Actions: Resolve (only when needs attention) opens a modal with a required note. Cancel (only when awaiting payment) opens ConfirmTyped with CANCEL. Both disabled with a tooltip otherwise; the rule text comes from the backend's 409 message if it ever fires.
  • Not found: "No order TPK-9999. Check the number on the board." + back link. Invalid format never calls the API.

Menu /menu board

  • Table: name, window, price, portions (inline stepper, optimistic with If-Match), available (inline switch, optimistic), offered-now chip, edit.
  • "Add item" opens ItemEditorDrawer in create mode; id is derived from name (slug) and editable until saved.
  • Edit drawer: all fields; price as naira integer with "₦" prefix; save sends PATCH with If-Match. 409 → "Changed elsewhere, reloaded" and the form refills from the server copy.
  • Empty: "No items yet. Add your first dish." Error: ErrorState.
  • Low stock rows get a caution chip; zero gets critical "Sold out".

Settings /settings pass

  • Three cards: Kitchen (name, pickup address, rider phone, prep minutes, pending TTL, low-stock threshold), Windows (six time inputs with live validation: "orders close must be before kitchen closes"), Delivery zones (small board: name, fee in naira, active switch; add zone inline).
  • One Save per card; PUT with If-Match; success toast "Saved"; 409 handled as in Menu.
  • A readOnly "Now" line shows the computed window from the server so the vendor sees the effect of their times.

Activity /activity board

  • Filters: tool (select), outcome (ok / error). Infinite list.
  • Row: time (mono), tool, chip ok/error with code, latency, order link. Expand → two mono panes, args and result, JSON pretty-printed; a Copy button.
  • This is the screen the recording lingers on when the tools fire.

Login /login pass

  • Centered card, brand mark, email + password, Sign in. Errors inline from the envelope message. 429 shows the countdown and disables the button.

Errors and feedback

ApiError

// shared/api/errors.ts
export const ErrorCode = z.enum(['validation','malformed_json','unauthenticated','invalid_credentials','token_revoked',
  'not_found','conflict','invalid_state_transition','version_conflict','business_rule','idempotency_mismatch',
  'rate_limited','upstream_unavailable','internal','network','timeout','contract_drift']);

export class ApiError extends Error {
  code: ErrorCode; status: number; message: string;           // message = envelope message, verbatim
  fieldErrors: { field: string; message: string }[]; retryAfter?: number; requestId?: string; current?: unknown;
  static from(res: Response, body: unknown): ApiError           // unknown envelope → 'internal' with a generic message
  get retryable() { return ['network','timeout','upstream_unavailable','internal'].includes(this.code) || this.status >= 500 }
}
  • Branch on code. Display message. Never branch on the message; never show a raw code to the vendor.
  • fieldErrors map onto form fields by name; the backend returns all of them at once and the form shows all of them at once.
  • version_conflict carries current (the server object) so forms can refill without a second request.
  • A zod parse failure at the seam becomes contract_drift, logged to console with the path, shown as "Something changed on the server. Reload." This is a bug class we want loud.

Where errors show

SituationSurface
Query fails on first loadErrorState in place of the part, with Retry
Query fails on background refetchKeep showing data; small caution toast "Couldn't refresh, showing last known"; LiveChip unaffected
Mutation failsCritical toast with the envelope message; form stays open with field errors
401Redirect to login with next; one neutral toast "Please sign in again"
429Inline countdown using retryAfter
Route-level crasherrorComponent with a plain message and a "Back to board" link; never a blank page
Chunk load failure after a deployGlobal handler reloads once

Toast rules

  • Success toasts are short and only for mutations ("Saved", "Order resolved", "Demo reset").
  • No toast for things the UI already shows (a new order arriving animates in; it does not also toast).
  • Tone comes from the semantic enum; the toast has no palette of its own.

Seam contract with the backend

Wire types in shared/api/types.ts are zod schemas inferred to TS types, written by reading the Go JSON tags, never from memory. Casing is snake_case on the wire and stays snake_case in the schemas; the UI does not rename fields.

export const Order = z.object({
  order_no: z.string(), status: OrderStatus, customer_name: z.string(), phone_masked: z.string().nullable(),
  fulfilment: z.enum(['delivery','pickup']), zone: z.object({ id: z.string(), name: z.string() }).nullable(),
  address: z.string().nullable(), window: z.enum(['lunch','evening']), lines_summary: z.string(),
  total_kobo: z.number().int(), total_display: z.string(),
  reference: z.string().nullable(), paid_at: z.string().datetime().nullable(),
  ready_by: z.string().datetime().nullable(), ready_by_wat: z.string().nullable(),
  confirmed_by: z.enum(['mcp','reconciler']).nullable(), attention_reason: z.string().nullable(),
  created_at: z.string().datetime(),
}).passthrough();                                   // unknown fields tolerated (additive API changes)

export const Page = <T extends z.ZodTypeAny>(item: T) => z.object({
  data: z.array(item), meta: z.object({ next_cursor: z.string().nullable(), has_more: z.boolean() }) });
  • ✔ Field names match the Go serialiser; a drift fails loudly as contract_drift.
  • ✔ Money: integer kobo + display string; the UI renders the string. No / 100 anywhere (lint rule greps for it).
  • ✔ Dates: ISO strings; relative time ("2 min ago") is the only client-side formatting, and only for created_at in activity rows.
  • ✔ Nullable fields are .nullable(), not optional; empty arrays are [].
  • ✔ Pagination names are exactly meta.next_cursor and meta.has_more.
  • ✔ The error envelope's code enum in errors.ts is the backend's list, copied, with the three client-only codes added.

Responsive layout and motion

The vendor's phone is the primary device; the laptop is for the recording. Every screen is designed phone-first and widened, not the other way round. Motion is deliberate and inventoried: each animation below has a reason, a duration token and a reduced-motion fallback.

Breakpoints and what changes

Topbar collapses to vendor name + LiveChip; window chip moves under it. Stat tiles 2×2. Board rows become two-line cards (status + order no + total / customer + lines).
